#### Вывод о масштабируемости
```
Для матрицы размером 20000×20000 достигнуто ускорение до 10.2× 
при 8 потоках, что объясняется эффективным использованием кэш-памяти 
и соблюдением NUMA-локальности данных благодаря стратегии first-touch policy: 
каждый поток инициализирует и обрабатывает свою часть матрицы, что минимизирует обращения к «удалённой» памяти.  

Для более крупной задачи (40000×40000) максимальное ускорение составило 8.9× при 7 потоках. 
При дальнейшем увеличении числа потоков (16–40) наблюдается насыщение и незначительное снижение ускорения, 
что связано с тем, что DGEMV является memory-bound задачей: арифметическая интенсивность низка.
```

#### Вывод о масштабируемости 
```
Ключевое - каждый поток считает свою часть суммы в локальной переменной, а потом один раз добавляет её к общей через #pragma omp atomic. Это позволяет избежать ошибок, которые бывают при простом sum += ....
Результаты для 40 000 000 точек:

    На 1 потоке: ~0.10 сек  
    На 8 потоках: ~0.022 сек → ускорение ~4.9×  
    На 40 потоках: ~0.014 сек → ускорение ~7.8×

То есть:
Чем больше потоков - тем быстрее программа.
Ускорение растёт, но не линейно: на 40 потоках мы получаем не 40×, а ~7.8×.
Это нормально - потому что даже параллелизме есть накладные расходы: создание потоков, синхронизация, работа с памятью.
```
